# --- M7.2: AI Execution Platform - concrete Provider Clients only ------------
# (app/ai_gateway/providers/*_client.py). Nothing above this line (and
# nothing in app/ai_gateway/, app/ai_agents/, or app/prompt_builder/
# outside providers/) may import these directly - see
# app/ai_gateway/providers/registry.py's own docstring for the grep rule
# this convention is meant to make enforceable. Versions current as of
# 2026-07-19 (anthropic 0.116.0, openai 2.46.0, google-genai 2.12.1) -
# verify against PyPI before upgrading; these SDKs release frequently.
#
# httpx compatibility review (triggered by a real `pip install` failure -
# ResolutionImpossible - during Docker build): google-genai==2.12.1 pins
# httpx>=0.28.1,<1.0.0 (per its pyproject.toml on GitHub,
# googleapis/python-genai tag v2.12.1) - strictly incompatible with this
# project's prior httpx==0.27.0 pin. Checked the other two SDKs' own
# httpx constraints before picking a fix, rather than blindly bumping:
# anthropic==0.116.0 pins httpx>=0.25.0,<1 ; openai==2.46.0 pins
# httpx>=0.23.0,<1. The three ranges intersect at [0.28.1, 1.0.0) - and
# 0.28.1 (released 2024-12-06) is still the newest stable httpx release on
# PyPI as of this check (only unreleased 1.0.0 pre-releases exist beyond
# it), so 0.28.1 is not just "a" compatible version, it is the ONLY
# concrete version every pinned SDK here currently accepts. No SDK
# version swap was a better fit than the httpx bump: downgrading
# google-genai below 2.12.1 to avoid its httpx>=0.28.1 floor was
# considered and rejected - older google-genai releases are further
# behind the SDK's own active development, and the httpx bump itself
# turned out to be a genuine no-op for this codebase's own usage (see
# httpx's own comment above), so there was no real tradeoff to prefer a
# different SDK version over.
#
# pydantic compatibility review (second real ResolutionImpossible from
# the same Docker build, surfaced only after the httpx fix above):
# google-genai==2.12.1 also pins pydantic>=2.12.5,<3.0.0 (verified
# against its pyproject.toml on GitHub) - incompatible with this
# project's prior pydantic==2.7.1 pin. Before bumping, checked: (1)
# whether an EARLIER google-genai release stays on a looser pydantic
# floor - bisecting release tags found v1.0.0 through v1.45.0 declare
# pydantic>=2.0.0 (compatible with 2.7.1), but that line is roughly 8+
# months behind 2.12.1 and not the actively developed one - not a good
# trade for a brand-new feature; (2) whether pydantic 2.12.5 breaks
# fastapi==0.111.0 or pydantic-settings==2.2.1 - both declare
# open-ended-above pydantic constraints (see each package's own comment
# above) and are satisfied; (3) pydantic's own changelog between 2.7.1
# and 2.12.x for breaking API changes relevant to a FastAPI CRUD app -
# no removal of `Config`/`@validator`/`.dict()`/`parse_obj` (still
# deprecated-but-functional, unchanged from 2.7.1's own behavior); the
# one real behavioral change is `serialize_as_any` handling, and this
# codebase's entire app/schemas/ tree (67 files checked) uses only
# modern v2-native idioms already (model_config = ConfigDict(...),
# from_attributes, model_dump, model_validate) with ZERO usage of
# `serialize_as_any`, `@validator`, `@root_validator`, `class Config:`,
# `.dict()`/`.json()` on a pydantic model, `parse_obj`, `orm_mode`, or
# `from pydantic import BaseSettings` anywhere - so this bump has no code
# to actually break here. pydantic 2.12.5 also requires Python >=3.9
# (raised from 2.7.1's >=3.8); this project's Dockerfile already targets
# python:3.11-slim, well above that floor. Net: low risk, confirmed by
# code inspection rather than assumed - pinned pydantic==2.12.5 exactly
# (the precise floor google-genai requires, not the newer 2.13.4 also on
# PyPI - see pydantic's own comment above for why the narrower pin was
# preferred).

openai==2.46.0
